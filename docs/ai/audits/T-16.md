## SPEC notes
- **CU-12 (delete):** begin transaction, lock the product with `UPDLOCK` (`PRODUCT_NOT_FOUND`), then `Product.Delete` (`PRODUCT_INACTIVE`, then RP-08 `PRODUCT_HAS_STOCK`). The domain writes reason `Discontinued`, `DeactivatedAt` and `DeactivatedBy`. `DeleteAsync` runs the conditional UPDATE, and the handler commits and returns `Unit` (204).
- **CU-13 (deactivate):** same flow, with `Product.Deactivate(ProductDeactivation)` enforcing RP-09/RP-10. The validator checks the reason enum, notes of at most 500 characters (`Product.DeactivationNotesMaximumLength`) and notes required when the reason is `Other`; each failure produces a `VALIDATION_ERROR` keyed by `Reason` or `Notes`.
- **SEQ-06 concurrency:**
  - `DeleteSql` has `WHERE Id = @Id AND IsActive = 1 AND Stock = 0`; `SaveDeactivationSql` has `WHERE Id = @Id AND IsActive = 1`.
  - Both repository methods return `affectedRows == 1`.
  - A `false` result throws `PRODUCT_HAS_STOCK` (delete) or `PRODUCT_INACTIVE` (deactivate), as the diagram's "0 filas" branch requires. The `UPDLOCK` read is the user-approved design decision and does not contradict the spec.
- **Stock:** the UPDATEs set only the deactivation columns and `IsActive`, so `Stock` is never edited outside `ApplyDelta`.
