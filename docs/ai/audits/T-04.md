## SPEC details
- **Catalog:** `ErrorCode` has 22 values, matching the 22 rows of DOMAIN_LOGIC §6. `ErrorCatalog` has 22 entries, and `ErrorCatalogTests` guarantees one entry per code.
- **Titles:** match §6 exactly.
  - "Datos no válidos", "No autenticado", "Acceso denegado", "Recurso no encontrado", "Conflicto", "Conflicto de inventario", "Referencia no válida", "Error interno".
  - `INSUFFICIENT_STOCK` is the only code that uses "Conflicto de inventario".
  - Both 403 codes use "Acceso denegado".
- **Details:** all 22 `ErrorMessages` texts match §6 character for character, including accents, punctuation and wording.
  - Named placeholders `{areaCode}`, `{id}`, `{stock}` and `{quantity}` became `{0}` and `{1}`. The rendered text is identical.
  - `INSUFFICIENT_STOCK` takes `{0}` = stock and `{1}` = quantity, in the order the spec uses.
- **Status per code:**
  - `ValidationException` gives 400.
  - `NotFoundException` gives 404 (`AREA_NOT_FOUND`, `CATEGORY_NOT_FOUND`, `PRODUCT_NOT_FOUND`).
  - `ForbiddenException` gives 403 (`AREA_ACCESS_DENIED`).
  - `DomainException` gives 409 (all 11 conflict codes, including `INSUFFICIENT_STOCK`).
  - `InvalidReferenceException` gives 422 (`REFERENCED_AREA_INVALID`, `REFERENCED_CATEGORY_INVALID`, `RELATED_MOVEMENT_INVALID`).
  - Anything else gives 500 `INTERNAL_ERROR`.
  - `MapUnauthorized` gives 401 and `MapForbidden` gives 403 `FORBIDDEN`.
- **Wire code:** `ToWireCode` turns PascalCase into UPPER_SNAKE. Tests check every code string (for example `AREA_ACCESS_DENIED` and `REFERENCED_AREA_INVALID`).
- **SEQ-08:**
  - `IExceptionHandler` calls `Map`, builds the ProblemDetails and writes `application/problem+json`.
  - Unhandled exceptions return 500 `INTERNAL_ERROR` with a fixed text. The test checks that no internal text such as "SELECT" leaks.
  - Only the 500 case is logged at `Error` level with the full exception. Mapped exceptions are logged at `Information`.
  - Validation returns `ValidationProblemDetails` with `errors` grouped by property.
- **Pipeline:** `ValidationBehavior` runs every validator, aggregates the failures, throws `ValidationException` and skips `next` on failure. `Program.cs` registers it as the only pipeline behavior. Handlers do not catch exceptions.

## WARN notes (do not change the verdict)
- **WARN-1 (CC5):** `ProblemDetailsMapper.cs:12` hard-codes `https://httpstatuses.io/`. It is the ProblemDetails `type` identifier, not an environment setting. ADR 0010 shows exactly this value (`"type": "https://httpstatuses.io/409"`). It is therefore accepted.
- **WARN-2 (SPEC, deviation from docs/ai/09):** that doc said to customize both the JwtBearer events and `IAuthorizationMiddlewareResultHandler`. Only the second was done, to avoid touching `Api/Configuration`, which is outside T-04 scope. It covers 401 and 403 on endpoints that use policies, and the tests exercise it. **Resolved in Reverse Sync:** `docs/ai/09` now describes `ProblemDetailsAuthorizationResultHandler` as the only mechanism.
- **WARN-3 (SPEC, documentation):** the placeholders in `ErrorMessages` are positional (`{0}`), whereas DOMAIN_LOGIC §6 names them. The argument order per code is an implicit contract with the future throw sites. **Resolved in Reverse Sync:** `docs/ai/09` has an "Argumentos por código" table.
