## Evaluation of the implementer's choices
- **`GetByIdForUpdateAsync` with `WITH (UPDLOCK, HOLDLOCK)` and UPDATE by Id only:** acceptable. It serializes the RA-03 count against category creation that locks the parent area (T-11), as `SEQ-03` and the T-11 objective describe. Using the same lock for the update path is harmless.
- **`InsertAsync` returns the `Area` materialized from `OUTPUT inserted.*`, and errors 2601/2627 map to `DomainException(AreaCodeAlreadyExists, code)`:** correct. This closes the race between `ExistsActiveCodeAsync` and the INSERT. `Area` has a private parameterless constructor and private setters, so Dapper can materialize it.
- **ANSI `DbString` for `Code`:** correct. The column is VARCHAR(10) and the unique index stays usable (no implicit conversion).
- **Shared helpers `AreaValidationRules` and `AreaWriteRepositoryExtensions` (internal):** acceptable. They remove duplication and reuse the Area constants. The internal helper keeps the `NotFoundException(AreaNotFound, id)` logic in one place.
- **Validators with `OverridePropertyName` (`Code` / `Name`) and `CascadeMode.Stop`:** acceptable. The error keys stay in the shape of the DTO, and each field gets one message.
- **Handler parameter named `request`:** acceptable, because it matches the `Handle` signature of Mediator. `CreateAreaHandler` takes the DTO from `request.Request`.
- **Validators registered by hand in `Program.cs` as singletons:** acceptable as a human-approved extension. Observation: every new validator needs the same manual line. Assembly scanning would need FluentValidation.DependencyInjectionExtensions, which is outside the Tech Fence, so manual registration stays.
