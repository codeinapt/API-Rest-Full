# 08 · Base de datos, EF Core y Dapper

Esquema canónico: `.sdap/DATA_MINDMAP.md` §2.

## Reglas inquebrantables
- **Prohibido `FOREIGN KEY`.** Permitidos `UNIQUE` (filtrados por `IsActive = 1`) y `CHECK`.
- **EF Core solo lee.** Contexto `InventoryReadDbContext`:
  - `QueryTrackingBehavior.NoTracking` global;
  - sin `DbSet` expuestos fuera de `Persistence/Read`;
  - **nunca** `SaveChanges`.
- **Dapper solo escribe** (y lee el estado necesario dentro de la transacción del Command).
- **Esquema solo con DbUp.** Nada de migraciones EF ni `EnsureCreated`.

## EF Core (lecturas)
- EF **no** mapea las entidades de dominio, sino filas de solo lectura propias de la persistencia (`Persistence/Read/Models/{Table}Row`, `internal`), una por tabla, con las columnas de `DATA_MINDMAP` §2. Los enums se leen como `byte` y el repositorio los convierte al proyectar. Así el dominio no necesita constructores pensados para EF.
- `InventoryReadDbContext` (`internal`) fija `NoTracking` en `OnConfiguring`, aplica las configuraciones del ensamblado y convierte todo `DateTime` a `DateTimeKind.Utc` (`UtcDateTimeConverter`). `SaveChanges` y `SaveChangesAsync` lanzan `InvalidOperationException`.
- Las configuraciones fijan tabla, clave, longitudes e `IsUnicode(false)` en las columnas `VARCHAR` (`Code`, `Sku`), para que los parámetros no se envíen como `nvarchar` y se usen los índices.
- Las configuraciones (`IEntityTypeConfiguration<T>`) mapean tablas y columnas existentes. **No** se declaran relaciones de navegación con FK; los *joins* se escriben explícitos en LINQ.
- `HasQueryFilter(x => x.IsActive)` **no** se usa globalmente: el filtro `status` (`active | inactive | all`) se aplica de forma explícita en cada consulta, porque los detalles por `id` también devuelven inactivos.
- Proyección directa a DTO en el `Select`. Paginación con `Skip/Take`, más `CountAsync` sobre la misma consulta filtrada.
- Repositorio de lectura: `internal sealed class {Entity}ReadRepository(InventoryReadDbContext context) : I{Entity}ReadRepository`, registrado *scoped* en `DependencyInjection.cs`. La proyección es un `private static readonly Expression<Func<{Table}Row, {Entity}Response>> ProjectToResponse`, compartida por el detalle y el listado. El filtro `status` es un `switch` privado (`FilterByStatus`) sobre `IQueryable<{Table}Row>`. Cuando el DTO necesita columnas de otra tabla, la proyección es un método privado `ProjectToResponse(IQueryable<{Table}Row>)` que hace el *join* explícito y se aplica después de filtrar, ordenar y paginar: `CategoryReadRepository` une `Categories` con `Areas` por `AreaId` para obtener `AreaCode` (*inner join*: un área nunca se borra, solo se desactiva).
- Los filtros opcionales (`areaId?`) son otro método privado (`FilterByArea`) que devuelve la consulta intacta cuando el valor es `null`. Un id de filtro que no existe no es un error: devuelve un listado vacío (`SCREEN_FLOW` §4), así que no se valida contra la base de datos.
- Todo listado paginado tiene un orden **determinista** que termina en `Id` como desempate. Áreas: `Code`, `Id` (un `Code` puede repetirse entre áreas inactivas). Categorías: `Name`, `Id` (un `Name` puede repetirse entre categorías inactivas). Productos: el campo de `sortBy` en la dirección pedida y después `Id` **siempre ascendente**.
- `sortBy` se resuelve con una lista blanca (`switch` a expresiones), nunca con texto dinámico.
- `ProductReadRepository`: `Filter` encadena `FilterByCategory`, `FilterByStatus`, `FilterBySearch` y `FilterByLowStock`. `search` busca `Name.Contains(search) || Sku.Contains(search)` (EF lo traduce a `LIKE '%…%'` con escape; la collation de SQL Server no distingue mayúsculas). Un `search` nulo, vacío o solo con espacios no filtra, y no tiene límite de longitud. `lowStock` solo filtra cuando vale `true` (`Stock <= MinimumStock`, RP-14); `null` y `false` no filtran (ADR-0011). `Sort` es la lista blanca: un `switch` sobre `ProductSortField` que elige la expresión de clave y llama a un `OrderBy<TSortKey>(products, sortKey, direction)` genérico (`OrderBy` u `OrderByDescending`), seguido de `ThenBy(Id)`.
- `ProductReadRepository.ProjectToResponse` une `Products` → `Categories` (por `CategoryId`) → `Areas` (por `AreaId`), con *inner joins*, para leer `CategoryName` y `AreaCode`. Calcula `IsLowStock` en SQL (`Stock <= MinimumStock`), convierte `DeactivationReason` de `byte` al enum y construye `Deactivation` y `Reactivation` solo cuando `DeactivationReason` o `ReactivatedAt` no son `null` (el detalle de un producto inactivo devuelve sus datos de baja, CU-15).

## Dapper (escrituras)
- `SqlConnectionFactory` crea la conexión a partir de `INVENTORY_DB_CONNECTION`.
- `IUnitOfWork` abre la conexión y la transacción. Los repositorios de escritura reciben la conexión y la transacción del `UnitOfWork`.
  - Puerto (`Application`): `BeginTransactionAsync(ct)` y `CommitAsync(ct)`.
  - `UnitOfWork` (`Infrastructure`, *scoped*, `internal`) expone `Connection` y `Transaction` a los repositorios de escritura, que dependen de la clase concreta. Usarlos antes de `BeginTransactionAsync`, o empezar dos transacciones, lanza `InvalidOperationException`.
  - **Rollback:** si el handler lanza antes de `CommitAsync`, el `DisposeAsync` del ámbito libera la `SqlTransaction` sin confirmar y SQL Server la revierte. Los handlers no necesitan `try/catch`.
- Repositorios de escritura: `internal sealed class {Entity}WriteRepository(UnitOfWork unitOfWork)`, registrados como *scoped* en `DependencyInjection.cs`. El SQL va en constantes `private const string` (raw string literals) y cada llamada usa `CommandDefinition` con `unitOfWork.Transaction` y el `CancellationToken`.
- **Carga para modificar:** `GetByIdForUpdateAsync` lee la fila `WITH (UPDLOCK, HOLDLOCK)` y Dapper materializa la entidad de dominio (constructor privado y *setters* privados). El bloqueo serializa, por ejemplo, la desactivación de un área (RA-03) frente a la creación de una categoría en ella, que bloquea la misma fila del padre. Con la fila bloqueada, el `UPDATE` posterior filtra solo por `Id`.
- **Inserción:** `INSERT ... OUTPUT inserted.<columnas> VALUES (...)` con `QuerySingleAsync<Entidad>`. Devuelve la entidad persistida con su `Id` de identidad, y el handler mapea esa instancia.
- Los parámetros de columnas `VARCHAR` (`Code`, `Sku`) se envían como `DbString { IsAnsi = true, Length = <máximo> }`, igual que `IsUnicode(false)` en EF, para que se use el índice.
- Repositorio de escritura: `internal sealed class {Entity}WriteRepository(UnitOfWork unitOfWork)`, registrado *scoped* en `Infrastructure/DependencyInjection.cs`. El SQL va en constantes `private const string` (*raw string literals*) y cada llamada usa `CommandDefinition` con `unitOfWork.Transaction` y el `CancellationToken`.
- Puerto de escritura por entidad (ejemplo `IAreaWriteRepository`): `GetByIdForUpdateAsync` (carga la entidad `WITH (UPDLOCK, HOLDLOCK)` para serializar las reglas que dependen de otras tablas, p. ej. RA-03 frente a la creación de categorías), las comprobaciones (`ExistsActiveCodeAsync`, `CountActiveCategoriesAsync`), `InsertAsync(entity)` y `UpdateAsync(entity)`. `ICategoryWriteRepository` sigue la misma forma: `GetByIdForUpdateAsync`, `ExistsOtherActiveCategoryWithNameAsync(category)` (`... AND Id <> @Id`), `CountActiveProductsAsync`, `InsertAsync` y `UpdateAsync` (que también mueve la categoría al escribir `AreaId`). El área padre se bloquea con `IAreaWriteRepository.GetByIdForUpdateAsync`, que serializa la creación o el movimiento de una categoría frente a la desactivación del área (RA-03). `IProductWriteRepository`: `GetByIdForUpdateAsync`, `ExistsOtherActiveProductWithSkuAsync(product)` (`... AND Id <> @Id`, reutilizable al reactivar, RP-12), `InsertAsync`, `UpdateDetailsAsync` (solo `Name`, `Description`, `MinimumStock` y `UpdatedAt`, RP-06) `UpdateCategoryAsync` (solo `CategoryId` y `UpdatedAt`, RP-07), `DeleteAsync` y `SaveDeactivationAsync` (CU-12/CU-13, SEQ-06: solo las columnas de baja `IsActive`, `DeactivationReason`, `DeactivationNotes`, `DeactivatedAt` y `DeactivatedBy`; no tocan `UpdatedAt`). Las dos bajas son la excepción a «con la fila bloqueada, el `UPDATE` filtra solo por `Id`»: además del `UPDLOCK` del handler, repiten la condición de SEQ-06 en el `WHERE` (`AND IsActive = 1`, y `AND Stock = 0` solo en `DeleteAsync`) y devuelven `bool` (exactamente 1 fila afectada). Si se afectan 0 filas, el handler lanza `PRODUCT_HAS_STOCK {stock}` (borrado) o `PRODUCT_INACTIVE {id}` (desactivación) sin confirmar la transacción (doble barrera, `03-architecture-patterns.md`). Ningún método genérico `UpdateAsync` escribe la fila completa: cada operación de producto tiene su propio `UPDATE` con las columnas que cambia, para que nunca se toque `Stock` (RP-04); el `INSERT` omite `Stock` y deja que actúe el `DEFAULT (0)`. Al crear, la categoría se bloquea con `ICategoryWriteRepository.GetByIdForUpdateAsync` (serializa frente a RC-03) y el área se lee con `IAreaWriteRepository.GetByIdForUpdateAsync` solo para el `areaCode` de la respuesta. Al cambiar de categoría (CU-11) se bloquea primero el producto (`PRODUCT_NOT_FOUND`) y después la categoría destino con `ICategoryWriteRepository.GetByIdForUpdateAsync` (`REFERENCED_CATEGORY_INVALID` si no existe o está inactiva), el mismo orden que la edición de categoría (entidad y después padre); el bloqueo de la categoría destino serializa el cambio frente a su desactivación (RC-03). La violación de `UX_Products_Sku` (2601/2627) se traduce a `SKU_ALREADY_EXISTS`. Reactivación (CU-14, SEQ-07): `GetSnapshotWithAreaForUpdateAsync(productId)` devuelve `ProductAreaSnapshot(Product, AreaCode)` (`Application/Products/Ports/`); bloquea solo la fila del producto (`WITH (UPDLOCK, HOLDLOCK)`) y hace `JOIN` a `Categories` y `Areas` para leer `a.Code`, así T-21 (ajustes) lo reutiliza sin bloquear la categoría. Dapper lo materializa con *multi-mapping* (`QueryAsync<Product, string, ProductAreaSnapshot>`, `splitOn: "AreaCode"`). El handler bloquea después la categoría propia con `ICategoryWriteRepository.GetByIdForUpdateAsync` (orden producto → categoría): el bloqueo U frente a U serializa la reactivación con la desactivación de la categoría (RC-03), algo que el `EXISTS` del `UPDATE` no garantiza por sí solo bajo READ COMMITTED. `ReactivateAsync` escribe solo `IsActive`, `ReactivatedAt` y `ReactivatedBy` con `WHERE Id = @Id AND IsActive = 0 AND EXISTS (categoría activa)` y devuelve `bool`; con 0 filas el handler lanza `PRODUCT_ALREADY_ACTIVE {id}` sin confirmar. El SKU se comprueba antes con `ExistsOtherActiveProductWithSkuAsync`, y `ReactivateAsync` traduce también la violación de `UX_Products_Sku` a `SKU_ALREADY_EXISTS` (carrera entre la comprobación y el `UPDATE`).
- `InsertAsync` devuelve la entidad persistida materializada por Dapper desde `OUTPUT inserted.*`, para que la respuesta lleve el `Id` de identidad sin una segunda lectura.
- Las columnas `VARCHAR` (`Code`, `Sku`) se envían como `DbString { IsAnsi = true, Length = ... }`, para evitar la conversión implícita y usar el índice.
- **Siempre parametrizado** (`@Param`). Prohibido concatenar SQL.
- Las sentencias críticas son **condicionales** y se comprueban las filas afectadas:
  ```sql
  UPDATE dbo.Products
  SET Stock = Stock + @Delta
  OUTPUT deleted.Stock
  WHERE Id = @ProductId AND (IsActive = 1 OR @Type = 3) AND Stock + @Delta >= 0;
  ```
- **Movimientos (CU-16, SEQ-04):** `IProductWriteRepository.GetStockSnapshotAsync(productId)` lee la fila completa del producto **sin** `UPDLOCK` (el `Product` que reciben las fábricas). No se bloquea porque la concurrencia la resuelve el `UPDATE` condicional (ADR-0005). `ApplyDeltaAsync(movement)` ejecuta el `UPDATE` de arriba con `movement.ProductId`, `(byte)movement.Type` y `movement.Delta` (la condición `IsActive = 1` no se aplica a los ajustes, `Type = 3`, porque RM-08 los permite sobre productos inactivos; es el único punto que modifica `Stock`) y devuelve `int?`: el `deleted.Stock` del `OUTPUT` (stock previo), o `null` si se afectan 0 filas (`QuerySingleOrDefaultAsync<int?>`). Solo se devuelve `deleted.Stock` porque `movement.RecordStockChange(previousStock)` recalcula `ResultingStock` (RM-07, comprobado también por `CK_InventoryMovements_ResultingStock_MatchesDelta`). `ApplyDelta` **no** toca `UpdatedAt`: solo lo cambian las ediciones (`03-architecture-patterns.md`); el movimiento ya guarda su `CreatedAt`. `IMovementWriteRepository` (`Application/Movements/Ports`) tiene `InsertAsync(movement)`: `INSERT ... OUTPUT inserted.*` que devuelve el movimiento con su `Id` (`BIGINT`), con `Type` y `AdjustmentReason` enviados como `byte`/`byte?`; y `ExistsRelatedMovementAsync(adjustment)` (RM-06): `SELECT CASE WHEN EXISTS (... WHERE Id = @RelatedMovementId AND ProductId = @ProductId)` con los datos del propio ajuste (regla 7). No existe ningún `UPDATE` ni `DELETE` sobre `InventoryMovements` (RM-05).
- `sqlcmd` desactiva `QUOTED_IDENTIFIER` por defecto y los índices filtrados lo exigen: para probar a mano un `UPDATE` sobre `Products` hay que usar `sqlcmd -I`. SqlClient (Dapper/EF) ya lo activa siempre.
- Validación del padre en escrituras de catálogo: `SELECT ... FROM Categories WITH (UPDLOCK, HOLDLOCK) WHERE Id = @Id AND IsActive = 1`.
- Las violaciones de índice único (`SqlException.Number` 2601/2627) se traducen a `*_ALREADY_EXISTS`: el repositorio las captura con `catch ... when` y lanza `DomainException` (p. ej. `AreaCodeAlreadyExists` con el código). Si el `UPDATE` puede cambiar la columna única (el `Name` de una categoría), `UpdateAsync` también la traduce (`CategoryNameAlreadyExists`). Es la segunda barrera: el handler ya comprobó antes la unicidad con `ExistsActive*Async`.
- Los enums se envían como `(byte)` para encajar con `TINYINT`.

## Paginación
- `PaginationParameters` (`Application/Common/Pagination`): `record` no sellado con `Page` (1) y `PageSize` (20). Los `*QueryParameters` heredan de él. `CalculateItemsToSkip()` da el valor de `Skip`.
- `PaginationParametersValidator`: `Page ≥ 1` y `PageSize` entre 1 y 100, con `ErrorMessages.PageOutOfRange` y `ErrorMessages.PageSizeOutOfRange`. Los validadores de cada query lo reutilizan con `RuleFor(query => query.Parameters).SetValidator(new PaginationParametersValidator()).OverridePropertyName(string.Empty)` (ver `03-architecture-patterns.md`, Queries).
- `StatusFilter` (`Active`, `Inactive`, `All`) es el tipo del filtro `status` de áreas, categorías y productos.
- `PagedResponse<T>(items, pagination, totalCount)` calcula `TotalPages` redondeando hacia arriba (0 si no hay elementos).

## DbUp
- Scripts en `Infrastructure/Migrations/Scripts/NNNN_Description.sql` como **recurso embebido**, ejecutados en orden por nombre.
- `DatabaseMigrator` se ejecuta al arrancar la API: crea la BD si no existe y aplica los scripts pendientes (journal `SchemaVersions`).
- **Un script commiteado no se edita jamás.** Los cambios se hacen con un script nuevo.
- Los scripts son idempotentes en la medida de lo posible (`IF NOT EXISTS`).
- Scripts actuales: `0001_CreateAreas`, `0002_CreateCategories`, `0003_CreateProducts`, `0004_CreateInventoryMovements` (una tabla por script, con sus índices). El journal guarda el nombre completo del recurso (`Inventory.Infrastructure.Migrations.Scripts.0001_CreateAreas.sql`): **no se renombra** ni se mueve un script ya commiteado.
- Nombres de restricciones: `PK_{Tabla}`, `DF_{Tabla}_{Columna}`, `CK_{Tabla}_{Columna}_{Regla}` (p. ej. `CK_InventoryMovements_ResultingStock_MatchesDelta`), y los índices como en `DATA_MINDMAP` §2.
- `AdjustmentReason` obligatorio en ajustes: `CHECK (Type <> 3 OR AdjustmentReason IS NOT NULL)` (`MovementType.Adjustment = 3`).
- Arranque: `Program.cs` lee `INVENTORY_DB_CONNECTION` (`EnvironmentVariableNames.DatabaseConnection`), llama a `AddInventoryInfrastructure(connectionString)` y, tras `builder.Build()`, ejecuta `DatabaseMigrator.Migrate()` antes de servir peticiones.
- `DatabaseMigrator`: `EnsureDatabase` + `DeployChanges` con una transacción por script y log a `ILogger<DatabaseMigrator>`. Si un script falla lanza `InvalidOperationException` con el nombre del script, y la API no arranca.
- Los scripts se prueban contra SQL Server real en `Inventory.IntegrationTests` (T-24), no con tests unitarios.

## Índices
Los de `DATA_MINDMAP` §2. Un índice nuevo requiere su propio script y actualizar `DATA_MINDMAP` (lo edita el humano).
